01

Order journey at a glance

One request, two gates. The cart page and POST /api/v1/orders run the same validation rules — the second gate isn't a formality, it's the reason a race condition (item goes out of stock between page-load and tap) can never slip through.

02

Cart validation & guardrails

Everything you asked about here — stale availability, coupon drift, address-driven pricing, guest checkout — is one problem: the cart is a snapshot that ages. The fix is the same shape already used in CartValidationService: re-derive truth from the backend at every decision point, never trust what the client cached.

Why an item goes unavailable — and what greys it out

Three causes are already covered by ItemAvailabilityRule, ItemStockRule and RestaurantAvailabilityRule. The rest are real scenarios worth deciding on now, as new rule classes — each one is a new @Component, zero changes to the orchestrator.

UX treatment for every row above is identical, which is the point: replace the quantity stepper with a disabled “Currently unavailable” chip, dim the line to ~55% opacity, and leave the item visible rather than silently vanishing it — the customer added it on purpose and should see why it's gone, not wonder where it went. A whole-restaurant failure (row 3–4) applies the same treatment to every line in one pass instead of one rule firing per item.

Coupon validation follows the same split as items

CouponService already separates a non-committing preview() from an atomic recordUsage() — the cart page calls preview() on every load and every coupon-code entry (expired / usage-capped / below minimum order / not-first-order-only all surface immediately), and OrderService.placeOrder() re-validates through recordUsage() at the moment of truth. Wiring a CouponValidityRule into the same List<CartValidationRule> that already runs for items would fold coupon staleness into the identical grey-out mechanism above, instead of a second bespoke error path on the frontend.

Guest vs authenticated: who calculates what, and from where

The backend already draws this line correctly — /cart/validate and /orders require a bearer token; PricingController.deliveryQuote deliberately does not. A guest gets an estimate, never an authoritative price, because there's no saved address or order history to validate against.

IP geolocation is city/ISP-level accuracy at best, and wrong outright behind carrier NAT or a VPN — never treat it as better than a fallback of last resort, and never let a guest estimate silently become the checkout price. Real checkout still requires a JWT either way, since /cart/validate and /orders are both authenticated — so the guest path only ever has to answer “roughly what will this cost me,” not “what will I be charged.”

Mixed carts, address changes, and the payable total

Product decision needed

Two of your requirements read as in tension and need one explicit answer: “show the total based on available items only” vs. “if items are unavailable, don't proceed to payment.” Recommended reading — do both, in sequence: display the available-only subtotal live (so the customer isn't staring at a number that includes a greyed-out item), but keep Proceed to Payment disabled while any line, the coupon, or the delivery quote is invalid. The customer removes or waits out the unavailable line, the total updates, the button unlocks. The alternative — auto-checkout silently dropping unavailable items — trades a clearer button state for a real risk: the customer pays for a different order than the one they thought they placed. Flagging this rather than assuming it.

Concretely: CartValidationResponse carries an availableSubtotal computed only over lines that pass every rule, plus an unavailableCount; the frontend renders that subtotal unconditionally, and gates the CTA on issues.isEmpty() — the same boolean the diagram in §01 branches on.

Address change is not a new problem — it's the existing endpoint, retriggered. computeDeliveryCharge() already takes lat/lng as input, so when an authenticated customer swaps the delivery address on the cart page, the frontend simply fires the same POST /cart/validate again with the new address id. No new backend surface; just an event binding (“on address change → re-validate”, debounced) that doesn't exist on the frontend yet.

Finally: cancellation policy copy is a static content block, not a validation rule — render it at the bottom of the cart page from a CMS/config value (or a constant if there's no CMS yet) rather than hard-coding it into a component, since refund-window policy is the kind of thing legal/ops will want to change without a deploy.

03

Pricing & distance decomposition

Your first question — “should distance calculation be its own service?” — has a precise answer once you look at what's actually there: OrderPricingService today computes tax, restaurant commission, delivery charge, and raw Haversine geometry in one class. That's a Single-Responsibility violation, but the fix is a package boundary inside order-service, not a new deployable — a network hop for a sub-millisecond Haversine call adds latency and a failure mode for no benefit at this scale.

The payoff for keeping DistanceCalculator as an interface rather than inlining Haversine: when road-distance (OSRM / Google Distance Matrix) eventually replaces straight-line distance, it's a second bean behind the same seam — see §06 — not a rewrite of pricing.

04

Driver assignment & matching Open gap

Worth stating plainly: no matching algorithm exists today. Assignment is a pull model — riders browse open orders and self-claim them. Every scoring factor you listed (rating, acceptance rate, idle time, traffic…) would be new, not an enhancement of something running.

Proposed matching engine — same shape as code already in this repo

Both existing strategy families (CartValidationRule, DiscountCalculator) follow one idiom: an interface, a handful of @Component implementations, collected by Spring into a List<T>, and orchestrated by one class that never grows an if/else per new case. A matching engine is the same idiom with a numeric result instead of a boolean.

Scoring formula, made unit-safe

Written literally, score = w1·d + w2·r + w3·t + w4·c + w5·i mixes kilometres, a 0–5 rating, a traffic index, a percentage, and minutes-idle in one sum — the weights would be doing unit conversion, not preference tuning. Normalize every factor to [0,1] first (and invert where “lower is better,” like distance and idle time), then weight:

score = w₁·(1−d̂) + w₂·r̂ + w₃·(1−t̂) + w₄·(1−ĉ) + w₅·(1−î)  where each x̂ ∈ [0,1] and Σw = 1

Vehicle type and rider preference are filters, not score terms — apply them as a pre-filter on the candidate pool (exclude non-matching vehicles / opted-out riders) before scoring runs, the same way availableOrders() today filters out self-pickup orders before a rider ever sees the list. Predicted demand belongs in §06 (surge), not the per-ride score — it's a pricing input, not a driver-ranking input.

06

Routing, ETA & surge Open gap

All distance today is straight-line Haversine — no routing engine, no ETA, no surge pricing exist. These are the most infrastructure-heavy asks on your list; scope them as later phases behind the seams already built in §03, not as day-one work.

Routing & ETA

Don't hand-roll A* — OSRM, GraphHopper and Google Directions already run contraction-hierarchy/A*-class pathfinding internally and are exposed as an HTTP call. The decision is which provider (self-hosted OSRM for cost control at scale vs. a managed API for zero ops burden), not whether to implement graph search in-house. Slot it behind the same DistanceCalculator interface from §03 as a second bean — OsrmDistanceCalculator or GoogleDistanceMatrixCalculator — selected by Spring profile, with Haversine kept as the always-available fallback when the routing provider errors or times out. ETA then becomes routeDistanceKm / avgSpeed × 60 using the routed distance instead of straight-line, which is what makes it trustworthy enough to show a customer a countdown.

Dynamic / surge pricing

None of the inputs the formula needs — demand density, weather, an events calendar, historical trends — have a data pipeline in this repo yet. Recommend landing the seam before the signals: a SurgeMultiplierStrategy interface with a NoOpSurgeStrategy (multiplier = 1.0) as the default bean, wired into PricingOrchestrator from §03 but inert. Nothing about today's pricing changes until a real strategy is built and flagged on.

surge = base × demandFactor × weatherFactor × trafficFactor  — each factor ≥ 1.0, each behind its own strategy bean, each optional

Build order matters here: demand/supply ratio (derivable from existing order + rider-availability data, no external dependency) is the only factor with data already in this system. Weather and event feeds are external integrations — treat them as separate strategy beans added independently, not a blocking dependency for shipping the demand-based multiplier first.

Proposed package layout

All additions stay inside the existing module boundaries — pureeats-order-service and pureeats-catalog-service — as new packages next to the strategy families that already live there. No new Maven module, no new deployable.

Adoption path

Sequenced so each step ships independently and nothing in production depends on a later step existing.

PhaseWorkRisk
1Extract DistanceCalculator + DeliveryChargeStrategy from OrderPricingService; behavior-identical refactor, same public APILow
2Add CouponValidityRule / DeliveryZoneRule to cart validation; wire frontend address-change → re-validateLow
3Wire guest geolocation cascade (browser → existing IpGeolocationService) to the existing public quote endpointLow

5Add DRIVER_ARRIVING / PAID states to the transition graphMedium
6Routing-provider integration (OSRM/Google) behind a second DistanceCalculator bean, Haversine as fallbackHigher — external dep
7Demand-based surge, then weather/events feeds as independent strategy beansHigher — new data pipelines

Phases 1–3 are pure refactors and low-risk additions to code that exists; phases 4 onward introduce genuinely new behavior and are where the team should re-review before building, per the “review architecture first” framing of this doc.
