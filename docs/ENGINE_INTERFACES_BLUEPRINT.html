00

How to read these diagrams

Every family below follows the same shape: one interface at the top, its implementations grouped into labeled categories underneath, one consumer to the side. Two relationship types, drawn the standard UML way so there's no ambiguity between "this class fulfills the contract" and "this class owns a list of them."

01

Distance Calculator

Today's only implementation is straight-line Haversine, living inside OrderPricingService (see the Order Journey Blueprint, §03, for why that's a Single-Responsibility problem worth fixing). Everything else below is on record for when road-distance or a caching layer becomes worth the complexity — none of it is required to ship the §03 refactor.

02

Delivery Charge Strategy

The three "core policy" implementations already exist — today as if/else branches inside OrderPricingService.computeDeliveryCharge() rather than separate classes. Extracting them is the whole §03 proposal in the Order Journey Blueprint; everything past that is new policy, not refactor.

Decorators here follow the same rule as the distance decorators in §01: they wrap a base strategy rather than being selected directly — SurgeAdjustedChargeDecorator takes a DeliveryChargeStrategy and a SurgeMultiplierStrategy (§05) in its constructor and multiplies the base result, so surge pricing never has to be re-implemented per charge policy.

03

Coupon Validity Rule

Not to be confused with DiscountCalculator (already live — PercentageDiscountCalculator, FlatDiscountCalculator, FreeDeliveryDiscountCalculator, indexed by DiscountType): that family answers "how much off," this one answers "is this code even usable right now." CouponService.validate() already runs the eligibility checks below — as sequential inline conditionals, not separate classes. Extracting them the same way as the cart rules turns "add a new eligibility check" from an edit into a new file.

04

Zone Containment (Polygon) Check

This is the missing piece behind DeliveryZoneRule in the Order Journey Blueprint's cart-validation table — "is this address inside a restaurant's serviceable area." Nothing in the codebase does point-in-polygon math today; catalog-service's DeliveryAreaCheckRequest/Response DTOs suggest the shape of this check was anticipated but not built out.

Build order that avoids overbuilding: start with CircularRadiusZoneCheck (a radius column on Restaurant, zero new geometry code), add RayCastingPolygonCheck when a restaurant genuinely needs a custom shape, and only reach for PostGisContainsCheck or GeohashBucketZoneCheck once per-request in-app polygon math shows up in a latency profile — premature geo-indexing is a common way this kind of feature turns into a multi-sprint detour.

05

Surge Price Engine

None of these signals have a data pipeline in the repo yet, so the priority isn't the strategy list — it's landing NoOpSurgeStrategy as the wired-in default first, so the seam exists and every other strategy is additive, never a cutover.

surge = base × demandFactor × weatherFactor × trafficFactor  — realized as CompositeSurgeStrategy multiplying a List<SurgeMultiplierStrategy>, capped by CappedSurgeDecorator
06

Driver Matching Engine

No matching or ranking logic exists in the repo today — assignment is a pull model (see §07). This is the full criterion catalog for the scoring engine proposed in the Order Journey Blueprint, §04, expanded with two filter-like criteria worth having on record even though they don't contribute to the score itself.

Normalization detail carried over from the Order Journey Blueprint, §04: every criterion returns a value in [0,1] (inverted where "lower is better" — distance, cancellation rate, idle time), so DriverMatchingEngine can sum weight() × score() across the whole list without the weights secretly doing unit conversion.

07

Driver Assignment Strategy

Easy to conflate with §06, so the boundary matters: Matching ranks — it answers "who's best." Assignment commits — it answers "how does a ranked list turn into one driver holding the order." DriverMatchingEngine can exist and simply feed a ranked list into today's pull model; nothing forces the two to ship together.

08

Routing Engine

All distance in the codebase today is straight-line Haversine — no routing engine exists. The one implementation deliberately included here as a caution rather than a recommendation is StaticGraphAStarRoutingEngine: hand-rolling A* over a self-built road graph. OSRM and GraphHopper already run contraction-hierarchy/A*-class search over real OpenStreetMap data — building this in-house means also owning map-data ingestion, which neither of the other eight implementations require.

09

ETA Calculation

The naive form — (distanceKm / avgSpeed) × 60 — is SimpleSpeedBasedEtaCalculator: a reasonable placeholder, and honest about its own limits once a real route exists to compare against.

10

End-to-end wiring

Every engine above slots into one of four moments in the order's life. Phases 1–2 exist today (see the Order Journey Blueprint, §01); phases 3–4 are where §06–§09 would actually get called if built.

Reading this against the adoption path — phase 1–2 engines (DistanceCalculator, DeliveryChargeStrategy, CouponValidityRule, ZoneContainmentChecker) are extensions of code that runs today and were staged as phases 1–3 in the Order Journey Blueprint's rollout table. Phase 3–4 engines (MatchingCriterion, DriverAssignmentStrategy, RoutingEngine, EtaCalculator) are the phase 4–7 items — genuinely new systems, reviewed here structurally before anyone estimates a build.

Reference catalog only — no source files were modified. Read alongside the Order Journey Blueprint for narrative flow and rollout sequencing; this document is the structural detail behind that narrative's Strategy-pattern proposals.
