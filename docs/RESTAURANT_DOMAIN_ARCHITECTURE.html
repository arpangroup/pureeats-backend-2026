System at a glance

A modular monolith — several Maven modules, one deployable Spring Boot process on one port — behind two separate React SPAs that both talk to it over REST.

Nothing on this row is a JPA @ManyToOne/@OneToMany — every relationship in this codebase is a plain id column plus a hand-written repository query. That's a consistent style choice across the whole domain model, not specific to Restaurant.

Serviceable location, in detail — why it's a dashed line above

Restaurant.locationId is a plain String column: no @JoinColumn, no FK constraint, and no query anywhere in the backend that filters or joins on it — the only two hits for getLocationId() in the whole codebase are the admin patch handler and the detail-response mapper, both just passing the value straight through. Location itself (name, description, is_popular, is_active) is unrelated to delivery-radius matching, which is computed entirely from latitude/longitude + deliveryRadius.

Gap

  • Admin panel picks a location from a dropdown and stores its id — that's the entire write path.
  • RestaurantSummaryResponse (every listing/card screen) doesn't include locationId at all; only the single-restaurant detail response does, and only as a bare id — never resolved to the location's name.
  • The customer app never reads locationId anywhere in its source.
04

How opening hours are stored

Two representations on the same row — one legacy, one current — and the backend does not keep them in sync. That sync is entirely a client-side responsibility today.

ColumnShapeWritten byRead by
opening_time / closing_timeTwo LocalTime columns — one daily windowRestaurantService create/patch, indirectly driven by the schedule editor (below)RestaurantAvailabilityRule and the customer app's getOpenStatus() — the only two places that decide "open now"
schedule_dataOne String column — JSON array of 7 {day, isOpen, slots:[{open,close}]} objectsRestaurantScheduleCodec.validateAndSerialize()RestaurantScheduleCodec.deserialize() → RestaurantDetailResponse.weeklySchedule, fed back into the admin edit form only

schedule_data reuses a column that pre-existed and sat completely unused before the weekly-hours feature was built — no migration needed, just a codec that validates known day names, rejects duplicate days, requires an open day to carry ≥1 slot, rejects overlapping/duplicate slots within a day, and requires each slot's close to be after its open.

The two columns are linked only in the admin form

Editing the weekly schedule derives the legacy window like this, client-side, on every change:

// RestaurantForm.tsx — WeeklyScheduleEditor onChange const firstOpenDay = schedule.find(d => d.isOpen && d.slots.length > 0) onChange('openingTime', firstOpenDay.slots[0].open) onChange('closingTime', firstOpenDay.slots[firstOpenDay.slots.length - 1].close)

"First open day found, its first slot's start, its last slot's end." A split lunch/dinner schedule (09:00–14:00 + 18:00–22:00) collapses into one continuous 09:00–22:00 window, and the choice isn't even day-aware — whichever day comes first in the list wins, regardless of what day it actually is today.

05

How open/closed is actually decided

Two independent implementations, both bypassing schedule_data entirely.

Backend — the checkout gate

// RestaurantAvailabilityRule.java (pureeats-order-service) if (restaurant.getOpeningTime() != null && restaurant.getClosingTime() != null && !isWithinOpeningHours(restaurant)) { return List.of(CartIssue.restaurantLevel( "This restaurant is closed right now (opens " + restaurant.getOpeningTime() + ")")); }

Runs on every cart validation and again inside OrderService.placeOrder() against the exact same rule list — so the page-load check and the real checkout gate can never disagree with each other. Both still only look at the single window.

Customer app — card and menu greying

// restaurantAvailability.ts (pureeats-customer-react-app) export function isRestaurantOrderable(restaurant): boolean { if (!restaurant.isActive || !restaurant.isAccepted) return false return getOpenStatus(restaurant.openingTime, restaurant.closingTime).isOpen }

A second, independent reimplementation of the same single-window logic — it even re-solves the overnight-wraparound case (e.g. 18:00–02:00) separately from the backend's version — reading a type that doesn't even request weeklySchedule.

If this gets fixed later

Not attempted here — this document is descriptive. The shape of a real fix: compute "open now" from schedule_data (today's weekday + current time against that day's slots) in one place — most naturally a backend-computed isOpenNow/opensAt/closesAt field added to the summary/detail responses, so neither the cart rule nor the customer app has to re-derive or duplicate the logic. The overnight-window handling already written twice, once in Java and once in TypeScript, is exactly the kind of logic duplication like this tends to let drift.
