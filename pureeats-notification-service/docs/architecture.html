Notification Service Architecture

The single module every other service goes through to reach a user — by email, SMS, push, WhatsApp, an in-app alert, or a console trace, on any combination of those at once. This page walks the class layout, the two live request flows, the async dispatch pool every request-path send now runs on, and the admin-configurable routing that decides which channel fires for whom.

Overview

Before this existed, notification logic was split across two unconnected paths — one hardcoded to alerts and Firebase push, one hardcoded to email/SMS OTP. Every module now depends on exactly one interface, NotificationService, and gets six channels, three swappable providers, and admin-editable routing for free.

PropertyHow it's achieved
Multi-channel fan-outone logical notification can hit several channels at once via sendToChannels(...)
Provider-swappableeach channel's real backend is chosen by @ConditionalOnProperty, not by editing the sender
Admin-configurable routingwhich channel(s) fire for which notification/role is a JSON blob in the settings table, editable at runtime
Zero-config safeevery provider defaults to a console/log stub — the whole stack works with no credentials configured
01

Design principles

  1. Two interfaces, full stop. Callers depend only on NotificationService (send one channel, or fan out to several) and channel senders depend only on ChannelNotificationSender. Nothing outside this module imports an SMTP client, an SMS SDK, or the Firebase Admin SDK directly.
  2. Provider swap = one class + one bean. EmailNotificationService/SmsNotificationService/WhatsAppNotificationSender each hold a provider interface; which concrete provider is active is chosen purely by config in NotificationProviderConfig.
  3. Fan-out, not one-channel-per-call. A login OTP or an order-status update can go out on several channels simultaneously — which ones is admin-configurable at runtime, not hardcoded per call site.
  4. New channel = new enum value + new sender. NotificationDispatcherService auto-collects every ChannelNotificationSender bean at startup — a new implementation registers itself just by existing.
  5. The provider round-trip never runs on a request thread. Every request-path call site uses sendAsync/sendToChannelsAsync, which hand off to a dedicated background pool. A slow SMTP relay adds to that pool's queue depth, never to the login or order-action response time.

Async dispatch

Every send method comes in two shapes — a blocking one for background jobs/tests, and an async one every HTTP-request-handling call site should use instead.

MethodRuns onUse from
send / sendToChannelsthe caller's own thread — blocks until the provider round-trip returnsbackground jobs, tests, anything already off the request thread
sendAsync / sendToChannelsAsyncnotificationTaskExecutorany HTTP-request-handling code path
 
flowchart LR
    Req["Request thread
e.g. login-challenge"] -->|sendAsync request| Pool[("notificationTaskExecutor
4-16 threads, queue 200")]
    Pool -->|runs on background thread| Send["send(request) — same
synchronous logic, just off-thread"]
    Send --> Result["CompletableFuture completes"]
    Req -.->|"await up to send-timeout-ms,
then respond either way"| Client["HTTP response"]
@Async only takes effect through the Spring proxy — calling this.sendAsync(...) from inside NotificationDispatcherService itself would bypass it and run synchronously, same as any Spring AOP method. Every caller reaches it through the injected NotificationService bean, so that's never an issue in practice.

AsyncNotificationConfig sizes and names the pool (notification.async.*), sets CallerRunsPolicy so a saturated queue degrades to synchronous-on-the-caller rather than dropping a notification, and calls setWaitForTasksToCompleteOnShutdown(true) so a deploy/restart doesn't kill a send that's mid-flight.

Flow · OTP notification

The primary channel still gates a hard failure if the provider responds within the timeout. What changed: a slow provider no longer holds the login response hostage — past security.otp.send-timeout-ms (default 2s), the flow responds optimistically and the real send finishes in the background. Extra channels were already best-effort; they're now also fully non-blocking.

Flow · Order-status notification

OrderNotificationService lives in order-service, not notification-service — order-service already depends on notification-service, catalog-service and user-service, so it resolves routing, senders, and the recipient's email/phone without a circular module dependency. Every channel here goes through sendAsync with no bounded wait at all — an order-status update was already a side effect of the state transition, never something the accept/cancel/deliver response depended on.

sequenceDiagram
    participant Order as Order*Service (order-service)
    participant ONS as OrderNotificationService
    participant Route as NotificationRoutingService
    participant Disp as NotificationService
    participant Pool as notificationTaskExecutor
    participant Senders as Channel sender(s)

    Order->>ONS: notify(role, userId, title, body)
    ONS->>Route: orderStatusChannelsFor(role)
    Route-->>ONS: e.g. CUSTOMER -> {IN_APP, PUSH}
    alt no channels configured
        ONS-->>Order: no-op (logged)
    else channels configured
        ONS->>ONS: resolve destination per channel
        loop each channel
            ONS->>Disp: sendAsync(NotificationRequest)
            Disp->>Pool: submit send(request)
            ONS->>ONS: .whenComplete(log outcome) — not awaited
        end
        ONS-->>Order: returns immediately
        Pool->>Senders: dispatch, independently, per channel
    end
All 8 order-lifecycle call sites (accept · cancel · assign-rider · deliver · admin-override · new-order-to-owner) go through this one method instead of a hardcoded notifyUser().

09

Extending it

Add a new channel (e.g. Slack)

  1. Add the constant to NotificationChannel.
  2. Write a ChannelNotificationSender implementation (@Service), returning that channel from channel(). Add a provider interface + config-selected bean(s) if it needs a swappable backend.
  3. Nothing else changes — the dispatcher picks it up automatically, and it's immediately valid inside NotificationRoutingConfig.

Add a new email/SMS provider (e.g. SendGrid, Twilio)

  1. Implement EmailProvider (or SmsProvider).
  2. Add one @Bean in NotificationProviderConfig, guarded by @ConditionalOnProperty(havingValue = "sendgrid").
  3. Set notification.email-provider=sendgrid. EmailNotificationService and every caller never change.

Known limitations

Destination reuse: extra-channel fan-out reuses one destination string per request. An EMAIL-primary OTP with an SMS/WHATSAPP extra channel configured would target an email address as a phone number — OrderNotificationService already resolves destinations per-channel correctly; the OTP fan-out in AuthenticationService does not yet.

Optimistic response: if the primary OTP channel takes longer than send-timeout-ms, the login flow says "OTP sent" before delivery is confirmed. A failure past that point is only visible in NotificationLog and the app logs, not to the user — a resend still works independently either way.

No durable queue: notificationTaskExecutor is in-memory. Graceful shutdown drains it, but a hard crash between "kicked off" and "actually sent" loses that notification with no retry.

What's next

Ranked by what would matter most for a production rollout — now that request-path sends are off the caller's thread, the next tier is mostly about reliability and observability of that background pool.

01

Real provider implementations

SendGrid/SES, Twilio/MSG91, and the real WhatsApp Business Cloud API — the architecture supports them today, nobody's written them yet.

02

Durable queue / message broker

notificationTaskExecutor is in-memory. Moving to SQS/RabbitMQ/Kafka means a notification survives a crash, not just a graceful shutdown.

03

Circuit breaker on slow/unhealthy providers

Right now every request pays the full send-timeout-ms wait even when a provider is known to be down. Fail fast after repeated timeouts instead.

04

Retry + dead-letter handling

A failed send just logs today. Exponential backoff for transient failures, a dead-letter table for exhausted ones.

05

Async pool observability

Queue depth, active/rejected counts, and per-send latency for notificationTaskExecutor aren't exposed to Actuator/Micrometer yet — right now the only signal is application logs.

06

Per-user notification preferences

Routing is currently admin-global per role — letting a customer opt out of PUSH/SMS per type, layered on top.

07

Stale push-token cleanup

FcmSender logs a warning on failure but never deactivates the token. FCM's "unregistered" response should flip isActive=false.

08

Uniform delivery logging

NotificationLog only covers EMAIL/SMS today — extending it to every channel gives one audit trail for "did this actually go out."

09

Admin template editor

Templates are classpath files today. Moving them into the Setting-backed config (like routing) lets admins edit copy without a redeploy.

10

Fix known edge cases + broaden test coverage

The destination-reuse mismatch above, plus none of the senders, the dispatcher, the routing service, or the new async/timeout paths have unit tests yet.
