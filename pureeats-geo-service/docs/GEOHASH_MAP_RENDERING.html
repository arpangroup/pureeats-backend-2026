Drawing GeoHash Boxes & Grids on a Real Map

LOCATION_DB.html explains how GeoHash and KD-Tree work as algorithms. This document explains the other half: how a GeoHash string turns into an actual rectangle on a Leaflet map, how a whole grid gets drawn and redrawn as you pan and zoom, and how you could visualize a KD-Tree's spatial partitioning the same way. Every code sample here is the real code already running in geo-delivery-simulator/index.html — this page just slows it down and puts it next to a live, editable version of itself.

Overview

What "Drawing on a Map" Actually Means

Every GeoHash, grid cell, or KD-Tree split in LOCATION_DB.html is, underneath, just numbers — a hash string, a pair of (lat, lng) ranges, a median coordinate. None of that is visible on a map by itself. "Drawing" it means one specific, repeatable conversion:

index / algorithm value  →  a pair of (lat,lng) corners  →  a Leaflet layer object  →  pixels on screen
      "tepgq6"                minLat/maxLat/minLng/maxLng      L.rectangle([...])          a green box you can see

Leaflet (and every other slippy-map library) already solves the hard part of this — projecting a latitude/longitude onto a pixel on your screen, at whatever zoom level you're at (Web Mercator projection, tile math, etc.). You never touch that layer directly. Your entire job, for everything in this guide, is producing plain {lat, lng} pairs and handing them to a Leaflet layer constructor — L.rectangle, L.circle, L.polyline, L.marker. Leaflet does the rest.

The Three Things That Need Drawing

This guide walks through three concrete rendering problems, each building on the last:

  1. One GeoHash cell — decode a hash string back into a box, draw one rectangle.
  2. A whole grid of cells — repeat step 1 across everything currently visible on the map, efficiently, and keep it correct as the user pans and zooms.
  3. A KD-Tree's spatial partition — not currently drawn anywhere in this codebase, but the same rectangle-drawing mechanics extend naturally to it, and doing so is one of the visualization upgrades suggested at the end of this document.
Relationship to the other two documents: LOCATION_DB.html teaches the algorithms (why GeoHash, how encoding works, why KD-Tree beats scanning). geo-delivery-simulator/ is the finished, interactive result. This document is the missing middle step — the actual glue code that turns one into the other — read alongside a small live version of each piece so you can watch it happen instead of just reading about it.

Phase 1: From GeoHash String to Rectangle

Step 1: What Encoding Throws Away (On Purpose)

GeoHash.encode(lat, lng, precision) (covered in LOCATION_DB.html Phase 4) repeatedly bisects the latitude range and the longitude range, keeps only the half the point fell into, and stops after precision × 5 bits. The hash string is really a record of which halves were kept — it is never the point's exact coordinates. That's the whole trick: two different points that happen to land in the same final half-range on every bisection produce the identical string.

Which means a hash string doesn't describe a point at all — it describes the rectangle left over after all that bisecting. Rendering a GeoHash is nothing more than recovering that rectangle.

Step 2: Decoding a Hash Back Into a Box

Decoding just runs the same bisection forward again, except instead of asking "which half is the point in," it reads the answer back out of the hash's bits and shrinks the range accordingly. This is geohashBounds() from the simulator, unmodified:

JavaScript
// geo-delivery-simulator/index.html — geohashBounds()
function geohashBounds(hash) {
  let latRange = [-90, 90], lngRange = [-180, 180];
  let evenBit = true;
  for (const c of hash) {
    const idx = GEOHASH_BASE32.indexOf(c);       // 1 character = 5 bits
    for (let n = 4; n >= 0; n--) {
      const bitN = (idx >> n) & 1;                // read one bit at a time, high to low
      if (evenBit) {                              // even bit position → this bit was a longitude split
        const mid = (lngRange[0] + lngRange[1]) / 2;
        if (bitN === 1) { lngRange[0] = mid; } else { lngRange[1] = mid; }
      } else {                                    // odd bit position → this bit was a latitude split
        const mid = (latRange[0] + latRange[1]) / 2;
        if (bitN === 1) { latRange[0] = mid; } else { latRange[1] = mid; }
      }
      evenBit = !evenBit;
    }
  }
  return { minLat: latRange[0], maxLat: latRange[1], minLng: lngRange[0], maxLng: lngRange[1] };
}

Walk it once by hand for a 2-character hash, precision-shortened for clarity: start with the whole planet, lat ∈ [-90,90], lng ∈ [-180,180]. Each of the 10 bits (2 chars × 5 bits) halves either the latitude or the longitude range, alternating, starting with longitude:

bit 1 (lng)  →  lng shrinks to [  0, 180]  or  [-180,   0]
bit 2 (lat)  →  lat shrinks to [  0,  90]  or  [ -90,   0]
bit 3 (lng)  →  lng range halves again within whichever half bit 1 picked
bit 4 (lat)  →  lat range halves again within whichever half bit 2 picked
  ...              (10 bits total for 2 characters)
result: a small lat/lng rectangle — NOT a point, a box

Precision is nothing but "how many times did we bisect" — every extra character is 5 more bisections, which is why cell size roughly quarters (halves in both dimensions) every ~2 characters. Phase 4 has the exact table.

Phase 2: One Box Becomes a Leaflet Layer

Step 3: The Coordinate-Order Trap

Once you have {minLat, maxLat, minLng, maxLng}, drawing it is one line:

JavaScript
const b = geohashBounds(hash);
L.rectangle([[b.minLat, b.minLng], [b.maxLat, b.maxLng]], {
  color: '#2f8f5b', weight: 1, fillOpacity: 0.03, dashArray: '3,3'
}).addTo(map);
The one bug this always produces the first time: Leaflet's own coordinate convention is [lat, lng]. GeoJSON, most geo APIs, and the intuitive "x,y" reading of a coordinate pair are [lng, lat]. geohashEncode(lat, lng, ...) above takes latitude first — but if you ever pipe a decoded box into something expecting GeoJSON (or paste coordinates from Google Maps, which shows lat,lng but some of its APIs want lng,lat), swapping them silently draws your rectangle on the wrong continent, not an error. There's no shortcut here beyond checking which convention every function you touch actually expects.

Step 4: Why a Rectangle, Not a Circle

It's tempting to think of a GeoHash cell as "roughly circular, roughly N km" — the simulator's own precision dropdown even talks in km. But a GeoHash cell is a literal axis-aligned rectangle in degrees, and because one degree of longitude covers less ground than one degree of latitude away from the equator, the same cell is not square in real-world meters except right on the equator. That's km in the dropdown label meaning "at this location," not a universal constant — draw the cell at high precision near a pole in the demo above and watch how much narrower it looks than one near the equator.

Phase 3: Drawing the Whole Grid

Step 5: Sampling the Cell Size Instead of Computing It

A grid needs to know the cell width and height in degrees before it can start stepping across the viewport. You could derive that arithmetically from the bit-allocation rule (how many of the precision × 5 bits went to longitude vs. latitude), but the actual code takes a much simpler shortcut: encode one point, decode it right back, and measure the box you get. Every cell at a given precision is the same size, so one sample tells you the step size for the entire grid:

JavaScript
// geo-delivery-simulator/index.html — drawGeohashGrid(), first few lines
const sample = geohashBounds(geohashEncode((sw.lat + ne.lat) / 2, (sw.lng + ne.lng) / 2, precision));
const latStep = sample.maxLat - sample.minLat;
const lngStep = sample.maxLng - sample.minLng;

Step 6: Walking the Viewport in Cell-Sized Steps

With a known step size, covering the visible map is a plain nested loop over the current map.getBounds(), re-encoding at each sample point, skipping any hash already seen (adjacent samples inside the same cell re-encode to the identical string), and drawing whatever's new:

JavaScript
const seen = new Set();
for (let lat = sw.lat; lat <= ne.lat + latStep; lat += latStep) {
  for (let lng = sw.lng; lng <= ne.lng + lngStep; lng += lngStep) {
    const hash = geohashEncode(lat, lng, precision);
    if (seen.has(hash)) continue;
    seen.add(hash);
    const b = geohashBounds(hash);
    const rect = L.rectangle([[b.minLat, b.minLng], [b.maxLat, b.maxLng]], {
      color: '#2f8f5b', weight: 1, fillOpacity: 0.03, dashArray: '3,3'
    });
    rect.bindTooltip(hash, { permanent: true, direction: 'center' });
    gridLayer.addLayer(rect);
  }
}

Note what this loop is not doing: it never computes a cell's corners by hand. It samples a point, asks GeoHash where that point belongs, and lets geohashBounds answer with the exact rectangle — the same "encode, then decode" round trip from Phase 1, just run in a loop instead of once per click.

Step 7: Redrawing on Pan, Zoom, and Precision Change

A grid computed once goes stale the moment the user drags the map — so the whole draw routine re-runs on Leaflet's own moveend event (fires after a pan or zoom settles), and again whenever the precision dropdown changes:

JavaScript
document.getElementById('geohashPrecision').addEventListener('change', () => { if (gridVisible) drawGeohashGrid(); });
map.on('moveend', () => { if (gridVisible) drawGeohashGrid(); });

Each call clears the previous grid layer's contents first (gridLayer.clearLayers()) rather than accumulating rectangles — otherwise every pan would leave the old grid behind, stacked under the new one.

Step 8: The Cell-Count Guard Rail

Zoom out far enough at high precision (say, precision 8 showing the whole city) and the nested loop above would try to draw tens of thousands of tiny rectangles — slow to compute, and unreadable even if it rendered instantly. The code estimates the cell count before looping and bails with a message instead:

JavaScript
const maxCells = 500;
const estCells = Math.ceil((ne.lat - sw.lat) / latStep) * Math.ceil((ne.lng - sw.lng) / lngStep);
if (estCells > maxCells) {
  L.popup().setLatLng(map.getCenter()).setContent('Zoom in for a readable GeoHash grid at this precision.').openOn(map);
  return;
}

This is the same "zoom-in-first" behavior every slippy map with a grid overlay uses (vector tile styles do the same thing with label density) — it's not GeoHash-specific, but it's the detail that keeps a naive "draw every cell in view" approach from ever becoming a real performance problem.

Phase 4: Precision & Cell Size

Every extra character adds 5 bits, alternating longitude/latitude, so cell dimensions roughly halve every character in one axis and every other character in the other:

Precision (chars)BitsCell width × height (approx, at the equator)
420~39.1 km × 19.5 km
525~4.9 km × 4.9 km
630~1.2 km × 0.61 km
735~153 m × 153 m
840~38.2 m × 19 m
945~4.8 m × 4.8 m

Two things worth internalizing from this table, both visible in the demos above:

  • Cells are never square in meters except at the equator — longitude bits and latitude bits are interleaved evenly, but a degree of longitude is narrower than a degree of latitude everywhere except the equator, so odd precisions in particular (5, 7, 9…) produce visibly rectangular, not square, cells.
  • The cell size is fixed once precision is fixed — unlike the bounding-box radius math in LOCATION_DB.html's Phase 2 (which depends on cos(lat) and the requested radius), a GeoHash cell at a given precision is exactly the same size everywhere on Earth at that latitude band. That uniformity is the entire reason GeoHash exists as an upgrade over a naive lat/lng grid (LOCATION_DB.html Phase 3's closing note) — and it's also the thing that makes a real grid legible enough to draw at all.

Phase 5: Drawing the Bounding-Box Query Itself

LOCATION_DB.html's Phase 2 (GeoUtils.getBox) computes a rectangular search box from a center point and a radius in km — deltaLat = radiusKm / 111, deltaLon = radiusKm / (111 × cos(lat)) — but that document never draws it. Rendering it uses the exact same L.rectangle call as a GeoHash cell; the only difference is where the four corners come from:

JavaScript
function drawBoundingBox(lat, lng, radiusKm) {
  const deltaLat = radiusKm / 111.0;
  const deltaLng = radiusKm / (111.0 * Math.cos(lat * Math.PI / 180));
  return L.rectangle(
    [[lat - deltaLat, lng - deltaLng], [lat + deltaLat, lng + deltaLng]],
    { color: '#a8650a', weight: 2, fillOpacity: 0.04, dashArray: '6,4' }
  );
}

The reason this is worth drawing at all — rather than trusting the formula — is visual: a bounding box is a superset of the true circular search radius. Overlay L.circle([lat,lng], {radius: radiusKm*1000}) on top of the same rectangle and the four corners stick out visibly past the circle. Those corners are exactly the false positives that LOCATION_DB.html's Phase 3 (getNearby's "doesn't actually guarantee a radius" note) and Phase 5 (Haversine as the final exact filter) both describe in prose — seeing the corner gap makes it obvious why a bounding box is only ever step one of a search, never the whole answer.

Phase 6: Drawing a KD-Tree's Spatial Partition

Step 9: A Tree Diagram Is Not a Map

LOCATION_DB.html's Phase 5 draws the KD-Tree as a binary tree — parent/child boxes connected by lines, the way you'd draw any binary tree. That's the right picture for understanding traversal (which branch to recurse into), but it says nothing about where on Earth each split actually falls. The geo-delivery-simulator doesn't draw this at all — its own README says plainly that KD-Tree is simulated as a sort, "behaviorally identical" for a handful of demo points but not the real structure. This phase fills that specific gap.

A KD-Tree build alternates the split axis by depth (latitude at depth 0, longitude at depth 1, latitude again at depth 2, …) and splits at the median point along that axis, same as LOCATION_DB.html's KDTree.build(). Spatially, each split is a straight line through the map: a latitude-axis split is a horizontal line at the median latitude (bounded to the current node's slice of the map); a longitude-axis split is a vertical line at the median longitude.

Step 10: Recursive Splitting Lines

This is the same recursive shape as the Java build() method in LOCATION_DB.html, except each call also draws a line instead of only linking nodes:

JavaScript
// bbox = { minLat, maxLat, minLng, maxLng } — the slice of the map this node owns
function buildAndDraw(points, depth, bbox, layerGroup) {
  if (points.length === 0) return;
  const axis = depth % 2; // 0 = split on latitude, 1 = split on longitude

  points.sort((a, b) => axis === 0 ? a.lat - b.lat : a.lng - b.lng);
  const medianIdx = Math.floor(points.length / 2);
  const median = points[medianIdx];

  if (axis === 0) {
    // horizontal line at median.lat, spanning this node's longitude slice
    L.polyline([[median.lat, bbox.minLng], [median.lat, bbox.maxLng]],
      { color: splitColor(depth), weight: 2, opacity: 0.8 }).addTo(layerGroup);
  } else {
    // vertical line at median.lng, spanning this node's latitude slice
    L.polyline([[bbox.minLat, median.lng], [bbox.maxLat, median.lng]],
      { color: splitColor(depth), weight: 2, opacity: 0.8 }).addTo(layerGroup);
  }

  const left = points.slice(0, medianIdx);
  const right = points.slice(medianIdx + 1);

  if (axis === 0) {
    buildAndDraw(left,  depth + 1, { ...bbox, maxLat: median.lat }, layerGroup); // below the line
    buildAndDraw(right, depth + 1, { ...bbox, minLat: median.lat }, layerGroup); // above the line
  } else {
    buildAndDraw(left,  depth + 1, { ...bbox, maxLng: median.lng }, layerGroup); // left of the line
    buildAndDraw(right, depth + 1, { ...bbox, minLng: median.lng }, layerGroup); // right of the line
  }
}

The key idea that makes this different from the GeoHash grid above: a KD-Tree's regions are not uniform rectangles. Every split's line length is clipped to the bounding box its parent split left behind, so dense clusters of points get many short, closely-packed lines while sparse areas get few, long ones — the partition adapts to your actual data, which is precisely the property that makes a KD-Tree worth using over a fixed grid once point density gets uneven (a scenario LOCATION_DB.html's Phase 3 closing note gestures at but doesn't visualize).

Suggested Visualization Improvements

Scoped strictly to GeoHash, the grid/index layer, and KD-Tree — not routing or the other simulator panels. Ordered roughly from smallest change to biggest.

  • Color grid cells by candidate density, not a flat fill

    Why: the current grid overlay (Phase 3 above) fills every cell with the same faint green regardless of how many stores/zones it holds. A simple count-per-cell → opacity or hue scale would make Stage 1 of the search pipeline ("which cell(s) have candidates") visible before a search even runs, instead of only after reading the pipeline log text.

  • Distinguish the exact-match cell from its 8 neighbor cells during a search

    Why: LOCATION_DB.html's Step 12 explicitly says a real GeoHash search checks the query cell and its neighbors, because a point can sit right next to a boundary it didn't cross. The simulator's current runSearch() only checks the exact hash match and falls back to every zone otherwise — visually indistinguishable from the neighbor-aware algorithm the docs describe. Drawing the exact cell one color and its 8 neighbors another would make the corner/boundary problem (and the current simplification) honest at a glance.

  • Overlay the bounding-box rectangle and the true-radius circle together

    Why: per Phase 5 above, this is described in text in two different documents but never actually drawn anywhere in the codebase. A rectangle-plus-circle overlay turns "bounding box gives false positives at the corners" from a sentence you have to trust into something you can see and click on.

  • Make the KD-Tree partition (Phase 6 above) a permanent overlay in the simulator, not just this doc

    Why: the simulator's own README says "KD-Tree is a sort" as a known simplification. It doesn't need a real KD-Tree implementation to fix the visualization gap — the recursive splitting-line drawing from Step 10 can run purely for display, over the same points already being sorted, so panels 3 and 4 show the actual spatial partition alongside the ranked list instead of a list alone.

  • Click a GeoHash cell to drill into its children (precision + 1)

    Why: a GeoHash cell is literally one level of nested quadrant subdivision (LOCATION_DB.html Step 10's bisection). A click-to-subdivide interaction would make that nesting tangible — and it's a natural place to also surface the "adjacent cells can have very different string prefixes right at a boundary" gotcha, since a child's neighbor across the parent's edge is often *not* a sibling in the hash string.

  • Animate the KD-Tree build depth-by-depth instead of drawing it instantly

    Why: Step 10's recursion is easy to read as code but the resulting picture, drawn all at once, reads as "a bunch of lines." A short delay per depth level (with the current depth's split highlighted and previous ones dimmed) turns the same drawing into a step-by-step animation of "split, recurse left, split, recurse left, …, backtrack" — which is exactly the traversal order LOCATION_DB.html's Step 15 nearest-neighbor search later depends on understanding.

  • Side-by-side GeoHash grid vs. the plain lat/lng Grid Index (Phase 3 of LOCATION_DB.html)

    Why: LOCATION_DB.html explicitly argues GeoHash exists to fix the plain grid's "not uniformly sized geographically" problem, but that claim is never shown — only stated. Drawing both index layers on the same map (toggleable) at comparable cell counts, especially somewhere far from the equator, would make the longitude-distortion difference visually undeniable instead of a paragraph to take on faith.
